# 接入窗口

Noxel 没有窗口层。`App` 产出线性 HDR 的 `Framebuffer` 并消费 `InputState`；呈现那个缓冲区是宿主的职责。这是 `adr/0002-no-dependencies.md` 的后果：窗口需要平台 API，而引擎不愿为它可能运行的每一个平台都背上一个。

本指南展示完整的宿主循环，以 `winit` 为例。
（`winit` 是*你的游戏*的依赖，不是引擎的。把它加进你自己 crate 的 `Cargo.toml`。）

---

## 契约

```text
your host
  ├── fill app.input_mut() from platform events
  ├── app.step(real_dt)
  ├── let image = app.resolve()      // sRGB bytes, width * height * 4
  └── upload image.pixels to a texture and present
```

有三件事要做对，而它们都很容易做错：

1. **用真实经过的时间步进，而不是常量。** `App::step` 喂给固定步长时钟，后者把时间摊成 0..n 次固定更新。传常量会让游戏在慢机器上以错误的速度运行。
2. **钳制长时间卡顿。** `GameClock` 已经限制了子步数并丢弃超出的部分，因此调试器暂停不会把玩家传送走。
3. **每帧只解析一次。** `resolve()` 会分配一张图像；每帧调用两次的宿主白白让这份开销翻倍。

## 主循环

```rust,no_run
use noxel_app::{App, AppConfig};
use noxel_render::framebuffer::ResolveSettings;

fn main() -> Result<(), Box<dyn std::error::Error>> {
    let mut app = App::new(AppConfig::default())?;

    // ... create a window and a surface with your platform library of choice ...

    let mut last = std::time::Instant::now();
    loop {
        let now = std::time::Instant::now();
        let dt = (now - last).as_secs_f32().min(0.25);
        last = now;

        // 1. Input: translate the platform's events into the engine's state.
        //    `app.input_mut().press(key)`, `.release(key)`, `.mouse`, `.scroll`.
        for event in /* your event source */ std::iter::empty::<()>() {
            let _ = event;
            // match event { KeyPressed(k) => app.input_mut().press(k), ... }
        }

        // 2. Simulate and render one frame.
        app.step(dt);

        // 3. Present.
        let image = app.resolve();
        // upload `image.pixels` (RGBA8) to your swapchain, then present.
        let _ = &image.pixels;

        if /* window closed */ false {
            break;
        }
    }
    Ok(())
}
```

## 像素完美呈现

引擎以 `AppConfig::internal`（默认 320x180）渲染，由你负责放大。两条规则让结果看起来像像素艺术，而不是一张模糊的低分辨率 3D 渲染：

- **最近邻过滤。** 内部缓冲区与窗口之间的线性滤波会把每一条硬像素边缘变成软边。
- **整数缩放倍率。** 在 1.5 倍下，一部分源像素覆盖两个目标像素、另一部分覆盖一个，于是窗口缩放时画面会闪烁。

`noxel-render` 中的 `Viewport` 会替你算出整数倍率：

```rust
use noxel_render::renderer::Viewport;

let viewport = Viewport {
    width: window_width,
    height: window_height,
    internal_width: 320,
    internal_height: 180,
    pixel_perfect: true,
};
let scale = viewport.integer_scale();          // 1, 2, 3, ...
let (w, h) = viewport.scaled_size();           // the letterboxed image size
let (ox, oy) = viewport.letterbox_offset();    // where to place it
```

把余下的部分做成黑边，而不是拉伸：320x180 的 16:9 宽高比填不满每一种窗口形状，而拉伸会毁掉画面。

## 输入

`InputState` 刻意是一个普通数据结构，而不是事件队列：

```rust
let input = app.input_mut();
input.press(65);          // held from now on
input.release(65);        // released; `was_released` is true for this frame
input.mouse = (x, y);     // in internal pixels
input.mouse_delta = (dx, dy);
input.scroll = ticks;
input.mouse_buttons[0] = true;
```

逐帧的边沿信息（`was_pressed`、`was_released`、`mouse_delta`、`scroll`）由 `App::step` 在帧末清除，而 `is_held` 会保留。失焦时调用 `release_all()` —— 否则窗口在后台时角色会一直走下去。

`movement_axis(up, down, left, right)` 返回归一化的 `(x, z)` 对，这正是俯视游戏想要的。

## 宽高比与相机

相机需要宽高比来构建投影：

```rust
let aspect = 320.0 / 180.0;          // the INTERNAL aspect, not the window's
let view = app.camera_mut().view(aspect);
```

改用窗口的宽高比，意味着可见世界会随窗口缩放而改变，这会让像素完美的缩放无法实现。引擎的约定是：内部分辨率定义视图，窗口只是它之上的一个视口。

## 常见错误

**「它以双倍速度运行。」**
你用常量 `dt` 步进，而 vsync 在 144 Hz 显示器上以 60 Hz 呈现。请传实测的经过时间。

**「alt-tab 之后玩家被传送了。」**
某一帧的 `dt` 是 30 秒。`GameClock` 限制了子步数，因此模拟不会真的跑 30 秒，但你也要钳制输入的 `dt`（`0.25` 是合理的上限）。

**「图像是模糊的。」**
线性过滤，或者非整数倍率。见上文。

**「世界看起来被压扁了。」**
你把窗口的宽高比传给了 `camera.view`。请传内部宽高比。

**「alt-tab 之后输入卡住了。」**
没有任何东西告诉引擎按键已经抬起。在失焦时调用 `input.release_all()`。
