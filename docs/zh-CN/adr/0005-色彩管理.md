# ADR 0005 — 线性 HDR 工作空间，每帧一次 sRGB 解析

**状态：** 已接受
**适用范围：** `noxel-render`、`noxel-asset`

## 背景

像素艺术以 sRGB 字节创作。光照、混合与色调映射在线性光下才是正确的。对 sRGB 值做算术，会让两次 50% 的透明混合出 75% 而不是 50%，会让光照衰减明显出错，也会让泛光发出错误颜色的光。

但逐像素、逐操作地来回转换既慢又有损——而有损在这里是致命的，因为整个美术方向都依赖于创作的字节能原封不动地到达屏幕。

## 决策

**帧缓冲存储线性 `f32` 辐射度。sRGB 转换每帧恰好发生一次，位于 `Framebuffer::resolve`，并带有向创作调色板的吸附。**

```
author -> Color8 (sRGB bytes)
       -> Color::to_linear()          (once, at load)
       -> linear f32 arithmetic       (all shading, blending, lighting)
       -> tone map + exposure         (once, at resolve)
       -> linear_to_srgb()            (once, at resolve)
       -> Color8 (sRGB bytes)         (on screen)
```

往返是**精确的**：对每一个可表示的值，`Color8 -> linear -> sRGB -> Color8` 都返回相同的字节。三个测试保证这一点：

- 光追路径中的 `unlit_surface_round_trips_its_colour`，以及光栅路径中的
  `unlit_sprite_round_trips_to_the_authored_palette`。
- `palette_round_trips_exactly`，它让 32 个调色板条目走完整条管线。
- `text_is_exactly_the_requested_colour`。

`Framebuffer::resolve` 提供三条色调曲线——`None`（光栅默认，因此往返精确）、`Reinhard` 与 `Aces`——外加曝光、抖动，以及可选的调色板吸附，以获得地道的受限调色板观感。

## 为什么用 HDR

自发光材质（一盏灯、一个法术特效）的辐射度高于 1.0。在着色点就钳到 1.0 会让泛光无法实现，也会压平每一处高光。把 `f32` 辐射度一直保留到解析，意味着泛光阈值有东西可供阈值化。

## 后果

- 仅颜色一项，帧缓冲每像素就是 12 字节（`f32 * 3`）。在 960x540 下是 6 MB，可以接受；4K 缓冲会是 100 MB，这就是引擎以某个内部分辨率为目标再做放大的原因。
- 抖动在 sRGB 转换之前的*线性*空间中应用，因此必须很小，否则会移动均值。测试断言均值移动至多 255 中的 4。
- 光线追踪模式默认 `ToneMap::Aces`，因为它产生真正的 HDR 辐射度；把它切成 `None` 会让明亮的自发光过曝裁切。

## 被否决的替代方案

- **sRGB 帧缓冲 + 逐操作转换**：正确但慢，而且反复转换恰好会在美术所关心的那些高光处有损。
- **线性 `u8` 帧缓冲**：精度不够；线性 8 位编码在暗部会明显出现色带。
- **完全不做色调映射**：对光栅路径没问题，但光线追踪器的反射与自发光需要一条曲线。
