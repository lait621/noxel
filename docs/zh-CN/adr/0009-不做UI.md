# ADR 0009 — 不做 UI 工具包

**状态：** 已接受

> **已被取代。** 下面的决定在它被写下时的需求下是正确的——当时不需要 UI/UX，
> 交付物是文档——而那个需求已经改变：引擎上现在跑着一个游戏，游戏需要时钟、快捷栏、
> 背包和商店。[ADR 0012](0012-UI层.md) 记录了这一反转，以及取代它的、更窄的边界。
> 这里的推理保持原样，因为它仍然是阻止新层变成框架的论据。

**适用范围：** 整个工作区

## 背景

游戏引擎会累积出 UI 层：主菜单、设置界面、调试控制台、关卡编辑器。每一个都是可观的子系统——布局、文本、输入路由、焦点、主题、本地化——而且每一个都要永远维护下去。

本项目最初的需求很明确：**不需要 UI/UX，交付物是文档。** 这是一个不寻常的约束，它值得一项架构决策，而不是被当作一种缺失。

## 决策

**Noxel 不提供 UI 工具包、不提供菜单系统、不提供编辑器。** 它提供的是：

1. **`noxel-debug`**——一套统计系统，带滚动百分位与区段预算；一个把文本面板与帧时间曲线画进帧缓冲的叠加层；以及一个带图像差异的无头帧转储器。
2. **`noxel-render::overlay`**——上面这些所基于的绘图原语：线、盒、射线、屏幕矩形、内置 3x5 字体与面板。它以所请求 sRGB 颜色的精确线性值绘入**线性**帧缓冲，因此 `#FF0000` 的叠加层解析回来恰好是 `#FF0000`。
3. **文档**——`docs/`，包含架构总览、快速上手、模块指南、API 参考与本 ADR 集。

调试叠加层明确*不是* UI 框架。它只负责绘制；它不做布局、焦点、输入路由或主题。它的存在是为了让开发者看见可见性、物理与 NPC 系统在做什么——剔除 bug 几乎无法从截图中猜出，而一旦能看见遮挡盒与相机到玩家的射线，它就一目了然。

## 后果

- 基于 Noxel 构建的游戏自带 UI，或用 `noxel_render::overlay` 画一个。`docs/guides/ui.md` 勾勒了后一种选择。
- 引擎在插件层之上没有「屏幕」或「状态机」的概念。插件是组合的单位，菜单就是一个插件。
- 文本渲染是 3x5 的大写位图字体。这对调试读数足够，并且刻意不足以支撑对话；需要文本的游戏自带字体图集，由 `noxel-asset::atlas` 打包。

## 被否决的替代方案

- **即时模式 UI 库**：一个体量庞大、接口面庞大的子系统，而且它需要一个窗口层（ADR 0002 已在默认构建中排除了这一点）。
- **保留模式场景图 UI**：对调试叠加层更差，而且会诱使游戏代码把它用于游戏 UI，而需求排除了这一点。
