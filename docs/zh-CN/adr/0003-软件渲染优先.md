# ADR 0003 — 软件渲染优先

**状态：** 已接受
**适用范围：** `noxel-render`

## 背景

Noxel 面向像素风俯视 RPG。参考分辨率为 320x180、480x270 与 960x540——每帧 5.8 万到 51.8 万像素，比现代 3D 游戏低一到两个数量级。一帧包含几千个三角形。

这个量级的引擎不需要 GPU，而为此付出的代价是三件在这里至关重要的事。

## 决策

**以 CPU 光栅化器和 CPU 光线追踪器作为默认渲染器。** GPU 后端是 feature flag 背后的显式扩展点（ADR 0007），而非必需项。

## 理由

**确定性。** 不做浮点重结合的 CPU 渲染器在每台机器上产出相同的字节。这正是黄金图像测试得以成立的前提：`noxel-debug::dump::compare` 可以断言某一帧与已提交的参考图*完全一致*，渲染回归会在 CI 中失败，而不是三周后被玩家注意到。GPU 的舍入、驱动的优化以及厂商相关的精度，使得这样的断言无法可移植地写出来。

**无需显示设备即可测试。** `App::run_headless(n)` 在 CI、构建服务器、没有 GPU 的容器里渲染真实帧。每一个子系统——可见性、NPC 人群、流式加载——都在真实图像上被验证。

**零依赖。** 软件路径不需要窗口库、不需要着色器编译器、不需要交换链。这是零依赖规则（ADR 0002）能在默认构建中成立的唯一方式。

## 如何保持快速

朴素的软件光栅化器在 320x180 下没问题；在 960x540 加 3000 个三角形下就不行了。四件事让它足够快：

1. **图块分箱。** 三角形通过计数排序（`TileBins`）分入 32x32 的屏幕图块。一个图块的三角形列表是连续的，因此光栅化一个图块只触及少量缓存行，而不必遍历整个场景。
2. **不相交分带并行。** 帧缓冲被切成若干行带，其 `&mut` 切片可证明不相交，因此 `JobPool::parallel_for` 可以并发光栅化各带，像素路径上没有锁、没有原子操作。并行与串行路径共用同一个 `raster_tile_in_band` 函数，并有测试断言二者产出相同像素。
3. **填充规则。** 共享的三角形边恰好被认领一次（`tie_owner`），这正是防止一块细分地面重复着色其内部接缝的原因——它在大型地板上表现为深色拼布，在四边形对角线上表现为过暗的透明。
4. **正确的提前退出。** 屏幕空间中的背面剔除、投影之前的近平面裁剪，以及逐片元的深度测试。

## 后果

- 阴影贴图、后处理与光线追踪器都跑在 CPU 上。在 320x180 下这是几毫秒；完整的光线追踪帧是一种「静帧」模式，而这正是它的用途。
- 混合模式（光栅化主通道 + 光线追踪阴影/AO）是推荐的高质量路径：它保留锐利的、像素对齐的主图像，并把光线预算花在看得见的地方。
- `Renderer` 是对象安全的 trait，因此 GPU 渲染器是即插即用的实现，而不需要重写它之上的系统。

## 被否决的替代方案

- **仅 GPU**：丢失确定性、可测试性与零依赖特性，换来的是本项目并不需要的性能。
- **GPU 优先 + 软件回退**：回退会腐烂；两条代码路径中只有一条被日常使用，等于一条代码路径加一项负债。
