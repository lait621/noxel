# ADR 0007 — GPU 后端是 feature-gated 的扩展点

**状态：** 已接受（设计），未实现
**适用范围：** `noxel-render`

## 背景

ADR 0002 禁止第三方运行时依赖，ADR 0003 让软件渲染器成为默认。GPU 后端需要 `wgpu`（或等价物），那是一棵庞大的依赖树，并且在某些平台上带有默认构建不应承担的链接期要求。

与此同时，一个永远无法使用 GPU 的 3D 引擎很难被认真对待，而两条既定需求——「支持光栅化与光线追踪」和「高性能」——最终都指向它。

## 决策

**GPU 后端现在完成规格说明，并在 feature flag 之后实现。**

- `noxel-render` 把 `Renderer` 暴露为**对象安全的 trait**。GPU 渲染器是该 trait 的一个实现；它之上的任何东西（可见性、app、npc、debug）都不变。
- 该 trait 的输入已经是 GPU 友好的形状：一个带 slot-map 句柄的 `Scene`，一个携带 `view`、`projection` 与 `view_projection` 的 `CameraView`，一个作为 `(instance handle, alpha, lod, distance)` 扁平列表的 `VisibleSet`，以及一个带线性 HDR 颜色的 `Framebuffer`。上传 `VisibleSet` 就是一次实例缓冲写入；`Mat4` 是列主序，因此无需转置即可上传；裁剪深度是 `[0, 1]`，因此直接匹配 WebGPU 与 Vulkan（ADR 0001）。
- feature 的声明会写成下面这样。**今天工作区里并不存在任何 `[features]` 表** ——
  这是实现将要采用的形状，而不是对当前代码树的描述；而引入 `wgpu` 会成为本项目
  有史以来第一个第三方依赖：

```toml
[features]
default = []
gpu = ["dep:wgpu"]        # not enabled by default; see ADR 0002
```

- 预期实现是一条分块的软件风格延迟管线：一个 G-buffer 通道写入 position/normal/albedo/material id，然后一个光照通道遍历同一份 `VisibleItem` 列表，原样复用 `noxel-render::light`，使灯光行为与 CPU 路径完全一致。
- GPU 上的光线追踪（DXR/Vulkan RT）**不在范围内**：CPU 追踪器是参考实现，而硬件光线追踪的可移植性不足以成为唯一路径。

## 会破坏什么

- **确定性**（ADR 0008）在 GPU 上无法达成。GPU 渲染器必须被排除在黄金图像测试之外，需要参考图像的测试必须跑在软件路径上。
- 没有 GPU 的**无头 CI** 需要 lavapipe/软件 Vulkan 路径。这是受支持的配置，但在这些分辨率下比 CPU 光栅化器更慢，这反过来削弱了 GPU 后端一开始的理由。
- **零依赖**仅对默认构建成立。

## 后果

选择「做规格说明而非做实现」是刻意的。移植点是真实且有测试的（该 trait 是对象安全的，`App` 已经在运行时于两个实现之间切换），因此增加第三个是机械性的工作。在需要之前就把它写出来，意味着维护一条 CI 无法验证的路径——正是 ADR 0003 警告过的回退腐烂。

## 被否决的替代方案

- **把 `wgpu` 作为硬依赖**：为一个像素艺术引擎的大多数用户并不需要的后端破坏 ADR 0002。
- **手写 Vulkan/Metal/D3D12 后端**：三个平台 API、零依赖，以及远超引擎其余部分总和的维护负担。
