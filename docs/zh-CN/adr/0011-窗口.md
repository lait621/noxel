# 0011. 窗口是一个 crate，而且是唯一的例外

状态：已采纳（2026-10）

> 本文是 [`docs/adr/0011-windowing.md`](../../adr/0011-windowing.md) 的中文翻译。英文版是权威版本，如有歧义以英文版为准。

## 背景

引擎没有办法打开窗口。它渲染到 `Framebuffer`，然后写 PNG——这对 CI 很友好，对「让我试试」很不友好。玩家会敲键盘，而按键是通过平台 API 送来的。

这与 [ADR 0002](0002-零依赖.md) 正面冲突。仅靠 `std` 打不开窗口：每个桌面操作系统都通过自己的工具包暴露窗口能力，只能靠 FFI 触达。可选项有三个：

1. **手写 FFI。** 在 macOS 上就是对 `NSApplication`、`NSWindow`、`NSView` 和一个运行循环调用 `objc_msgSend`，还要为每个平台各写一份。它需要 `unsafe`，而工作区里每个 crate 都禁止 `unsafe`；而且这类代码的典型特征是只在自己写它的那台机器上能跑。
2. **引入一个窗口 crate。** 正确、可移植、有人在维护——代价是一个依赖。
3. **不提供窗口。** 对引擎来说站得住脚，对用户来说毫无用处。

## 决策

**选 2，新建 crate `noxel-window`，依赖可选且默认关闭。**

这个 crate 被四面封住：

1. **只此一个。** 它是工作区里唯一带第三方依赖的成员。树里其他任何地方想加依赖，都需要再写一份 ADR。
2. **可选，默认关闭。** `winit` 和 `softbuffer` 藏在 `window` feature 后面。`cargo build --workspace` 和 `cargo test --workspace` 既不编译它们，也不下载它们，而且在完全没有网络的情况下依然可用——这一点是被断言的，不是被假设的。引擎的默认构建保住了 ADR 0002 换来的全部性质：不下载、无供应链、不跑陌生人的构建脚本。
3. **依赖方向是倒的。** `noxel-window` 依赖引擎；引擎不依赖它。接缝是一个 trait：`Host`，由这个 crate 定义、由调用方实现。`noxel-app`、`noxel-render` 以及它们下面的一切，都没听说过 `winit`。
4. **关闭时会大声报错。** 没有该 feature 时，`run` 返回 `WindowError::FeatureDisabled`，它的 `Display` 会打印出重新构建所需的那条确切命令。忘了开 feature 的调用方拿到的是一条指令，而不是链接期的符号缺失。

## 这个 crate 做什么，以及刻意不做什么

它做：

- 打开一个窗口，尺寸取内部分辨率的整数倍，余数做黑边。按 2.5 倍缩放的像素画会闪烁；这和 `Viewport::pixel_art` 是同一条规则，只是落实在像素真正落地的位置上。
- 把键盘与鼠标事件转换成 `Input`，并使用**引擎自己的键码**。`key::W == 87`，也就是 `b'W'`，所以 `movement_axis(87, 83, 65, 68)` 在窗口里和在引擎里都表示 WASD，中间没有任何映射表。
- 掌管实时循环：测量真实流逝时间、做钳制，然后交给 `Host::step`，后者再转发给引擎的固定步长 `GameClock`。模拟速率与帧率保持独立，而这正是 [ADR 0008](0008-确定性渲染.md) 所依赖的性质。
- 窗口失去焦点时释放所有按下的键。没有这一条，角色会在玩家去读邮件的时候一直往墙上撞。
- Escape 和窗口关闭按钮都能退出——这两件事不该让每个游戏自己实现。

它不做：

- **不用 GPU 绘制。** 它用 `softbuffer` 呈现帧缓冲，也就是 CPU 位块传输。这与 [ADR 0003](0003-软件渲染优先.md) 一致：渲染器是参考实现，窗口是显示器，不是第二个渲染器。GPU 路径是 [ADR 0007](0007-GPU后端.md) 的事，且仍未实现。
- **不实现游戏。** 没有场景图、没有菜单、没有资源加载——那些都在更上层。`Host` 只有四个方法。
- **不隐藏事件循环。** `run` 阻塞到窗口关闭为止，因为 `winit` 的事件循环就是这样，假装不是只会把平台细节泄漏回上层。

## 后果

- 有网络连接的开发者可以用一条命令玩到 demo：`./scripts/run-window.sh`。
- 只想改引擎的人依然什么都不下载。默认关卡——`cargo test --workspace`、`cargo clippy --workspace --all-targets -- -D warnings`、`noxel-gen verify`——没有任何变化，也依然可以离线运行。
- 开启该 feature 在 macOS 上会引入 **33 个 crate**——`winit`、`softbuffer`，以及它们需要的 objc2 绑定。`Cargo.lock` 解析出约 190 个包，默认构建既不编译也从不下载它们。这是看得见的代价，值得点明：lockfile 不再是二进制内容的完整描述。默认 feature 下的 `cargo tree -e normal` 才是，而它就是让这件事保持诚实的检查：

  ```text
  $ cargo tree --workspace -e normal | grep -v '^noxel-\|town-demo'
  (nothing)
  ```

- demo 现在同时是两样东西。没人按键时，它沿脚本路线行走并写 PNG——这是 CI 路径。一旦有移动键按下，控制权就归玩家，它变成一款游戏。这里没有模式开关；回退行为*本身*就是那个功能。
- 窗口无法做无头测试。被测的是它周围的一切：按键映射、位块传输的缩放与黑边算术、输入边沿处理、固定步长计时，以及 feature 关闭时的错误。事件循环本身靠运行二进制来验证，也就是 `scripts/run-window.sh` 所做的事。

## 被否决的替代方案

- **用 `wgpu` 表面取代 `softbuffer`。** 依赖更多、要求显卡驱动，而且会立刻多出一条与参考光栅化器分道扬镳的渲染路径。
- **把窗口放进 `noxel-app`。** 那会让每个引擎使用者都被强加一个平台依赖，无论他要不要——而这正是 ADR 0002 拒绝的那笔交易。
- **单独开一个仓库。** 那 demo 就无法演示引擎的真实 API，接缝也会腐烂。
- **自己写一个平台 crate 用 `unsafe` FFI。** 每个平台一百行去追平一个已经存在、且在我们没有的硬件上测试过的 crate。
