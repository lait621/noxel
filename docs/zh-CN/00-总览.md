# 总览

Noxel 是一个面向**俯视角像素风 RPG** 的轻量级 3D 引擎。你用三维的方式描述一个世界；玩家从上方看到它，内部渲染分辨率为 320x180（或者你选的任何值），再放大到窗口，因此最终画面读起来是像素画，而不是低多边形 3D 游戏。

本文是心智模型。它回答「这是什么、不是什么，以及其余一切都由之推导出的五个理念是什么」。请在阅读各篇指南之前先读它。

---

## Noxel 不是什么

把边界讲清楚，大家都省时间。

| 不是什么 | 原因 |
|---|---|
| 通用 3D 引擎 | 坐标、相机和光照都假定俯视视角。它也能渲染第一人称场景，但效果差、速度慢。 |
| UI 工具包 | 没有菜单、没有文本输入、没有布局。见 `adr/0009-no-ui.md`。 |
| 窗口层 | 没有平台 API。`Framebuffer` 由你自己呈现；见 `guides/windowing.md`。 |
| 模型导入器 | 没有 glTF/OBJ 加载器。几何体来自程序化图元和体素预制体；细节放在纹理里。参见 `04-rendering.md` 中与 `adr/0006` 相关的说明。 |
| 脚本宿主 | 没有内嵌语言。玩法逻辑用 Rust 写。 |
| 编辑器 | `tools/noxel-gen` 从代码生成资源，可 diff、可评审；没有 GUI。 |
| 依赖友好 | 默认构建**零**第三方 crate。见 `adr/0002-no-dependencies.md`。 |

## 五个理念

这个代码库里的一切都源自五个决策。把这些内化之后，剩下的都是细节。

### 1. 一个世界单位是一米，`+Y` 向上，`-Z` 向前

一个右手系、以米和弧度为单位的世界，裁剪深度范围为 `[0, 1]`。每个子系统——噪声、物理、寻路、流式加载——都说这一种语言，因此永远不会出现「这是以什么为单位的？」这种问题。
→ `adr/0001-coordinate-system.md`

### 2. 世界是 `(seed, address)` 的纯函数

区块 `(900, -400)` 的生成结果始终相同：无论玩家是走过去的还是传送过去的，无论在什么机器上、以什么顺序、是否并行。生成路径中任何地方都不存在共享的可变随机数生成器。
→ `adr/0006-deterministic-generation.md`

正是它让流式加载、存档、多线程和测试能够同时成立。这是整个引擎中最承重的决策。

### 3. 渲染同样是确定性的

没有任何渲染器会去读时钟、线程 id 或全局 RNG。同一帧产生同样的字节。这把渲染回归从「玩家三周后才发现」变成了一个失败的测试——与提交在仓库里的 PNG 做黄金图像比对。
→ `adr/0008-deterministic-rendering.md`

### 4. 由 CPU 渲染，而且有三种做法

默认是基于 tile 的软件光栅化器；光线追踪器也可用；**hybrid** 模式光栅化主可见性，并对次级光线（阴影、环境光遮蔽）做光线追踪——单位开销换来的画质提升恰恰在这里。
→ `adr/0003-software-renderer-first.md`、`adr/0004-dual-renderer.md`

### 5. 颜色一直到最后一刻都是线性的

一切都是线性 `f32` 辐亮度，直到每帧一次 resolve 把它转换成 sRGB。因此一个不受光照的 sprite 往返之后得到的是**恰好**美术所绘制的那些字节——两个渲染器里都有测试对此做断言。
→ `adr/0005-color-management.md`

## 一帧是怎么跑的

```text
                App::step(dt)
                      |
   +------------------+-------------------+
   |                                      |
fixed_update (0..n)                    frame_update
   |                                      |
   |  plugins.update(dt)                  |  camera.follow(focus, dt)
   |  physics.step(dt)                    |  streamer.update(focus)
   |  <- FIXED rate, so gameplay          |  visibility.update(...) -> VisibleSet
   |     is deterministic                 |
   +------------------+-------------------+
                      |
                    render
                      |
        +-------------+-------------+
        |             |             |
     Raster       Hybrid        Raytrace
        |             |             |
        +-------------+-------------+
                      |
                  overlays
                      |
                  resolve  ->  sRGB Image  ->  your window or a PNG
```

有两处顺序不是随意的：

- **相机先于流式加载和可见性。**否则世界会晚一帧才到，玩家会看到区块在身后冒出来。
- **玩法以固定频率运行，渲染则以机器能跑到的任意频率运行。**即便没有任何依赖，也没有理由让物理依赖帧时间。

## 数据流，以及谁拥有什么

```text
  seed + WorldConfig
        |
        v
  WorldGenerator  ---- pure function of (seed, chunk) ---->  Chunk
        |                                                      |
        |  sample_height / biome_at / is_road_at                |  tiles, heights,
        |  (answerable for ANY coordinate, no chunk needed)     |  colliders, props,
        v                                                       v  buildings
  WorldStreamer  <--- LRU around the camera --->  loaded chunks
        |                                                      |
        |                                                      |
        v                                                      v
  tile queries, walkability, colliders          scene meshes per chunk
        |                                                      |
        +-----------+--------------------+                     |
                    |                    |                     |
             PhysicsWorld          NpcSystem              Scene (instances)
             (bodies,      (crowds, pathing, steering)          |
              queries)                    |                     |
                    |                    |                     |
                    +----------+---------+---------------------+
                               |
                          AppContext
                               |
                        VisibilitySystem  ->  VisibleSet
                               |
                          Renderer  ->  Framebuffer  ->  Image
```

`AppContext` 是唯一一个能触达所有子系统的地方。插件拿到 `&mut App`，然后读 `app.physics`、`app.streamer`、`app.scene` 等等。

## crate 地图

| Crate | 一句话 | 依赖 |
|---|---|---|
| `noxel-core` | 数学、RNG、时钟、任务、对象池、空间结构、事件 | — |
| `noxel-ecs` | 稀疏集实体与组件、分阶段调度器 | core |
| `noxel-asset` | PNG、JSON、图像、纹理、图集、数据格式、热重载 | core |
| `noxel-render` | 帧缓冲、网格、材质、光源、场景、光栅化器、光线追踪器、叠加层 | core, asset |
| `noxel-camera` | 俯视相机装置、平滑、像素级吸附、抖动、区域 | core, render |
| `noxel-visibility` | 视锥/距离/尺寸/遮挡剔除、淡出、LOD | core, ecs, render, camera |
| `noxel-physics` | 刚体、SAT、求解器、角色控制器、查询 | core |
| `noxel-world` | 地形、生物群系、道路、城镇、流式加载、预制体 | core, asset |
| `noxel-npc` | 人群分层、A*、流场、转向、日程 | core, ecs, physics, world |
| `noxel-debug` | 统计、预算、叠加层、帧导出、图像差异比较 | core, render, asset |
| `noxel-app` | `App`、`Plugin`、固定步长帧循环 | 以上全部 |
| `tools/noxel-gen` | 资源生成器 | core, asset |
| `examples/town-demo` | 一个完整的村庄 | 所有 crate |

依赖**只朝一个方向**。这是一条规则，不是巧合：它意味着任何 crate 都能通过阅读它自身以及它下方的 crate 来理解，而且它上方的改动不会破坏它。

## 你能免费得到什么

这些本来都要你自己写，按你会注意到的顺序排列：

- **手感正确的相机。**死区、与帧率无关的平滑、前瞻、像素级吸附、边界钳制，以及基于 trauma 的抖动——可复现，而不是依赖时间。
- **可以看穿的相机。**当屋顶或树木挡在相机与玩家之间时，它会淡出；不再遮挡时又淡回来。这决定了俯视角游戏在室内能不能用。
- **屏幕之外不花一分钱的世界。**视锥、距离、屏幕尺寸和遮挡剔除，并附带一份剔除报告，精确说明是哪个阶段拒绝了什么。
- **人群。**分层模拟、共享流场、转向和每日日程——测试套件里还有一个实测的「每 agent 微秒数」。
- **可以拿来做游戏的物理。**带台阶翻越和坡度上限的角色控制器、射线与重叠查询、层、休眠、确定性步进。
- **一套完整的调试手段。**每个区段的滚动百分位数（而非平均值）、带预算线的帧时间曲线图，以及带图像差异比较的无头帧导出，让渲染回归直接导致 CI 失败。
- **由代码生成的资源。**`noxel-gen` 确定性地生成每一张纹理、图集、tileset 和预制体，因此美术资源可 diff。
