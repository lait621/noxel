# 架构

每个 crate、每个模块，以及一帧如何流经它们。

先读 `00-overview.md` 了解五个理念；本文是地图。

---

## 依赖图

依赖**只朝一个方向**——在这张图里就是向下。下方的东西对上方的东西一无所知。

```text
                          noxel-app
                 App, AppContext, Plugin, frame loop
                              |
     +----------+----------+--+--+----------+-----------+
     |          |          |     |          |           |
 noxel-npc  noxel-world  noxel-  noxel-   noxel-     noxel-
            (generation) physics  camera   debug      visibility
     |          |          |     |          |           |
     |          |          |     |          |           |
     +----------+----------+-----+----------+-----------+
                              |
                        noxel-render
                    (scene, raster, raytrace)
                              |
             +----------------+----------------+
             |                                 |
         noxel-ecs                        noxel-asset
             |                                 |
             +----------------+----------------+
                              |
                          noxel-core
```

两条规则让这张图保持有用：

1. **一个 crate 只能使用位于它下方的 crate。**如果下层 crate 需要上层 crate 里的东西，那么这个抽象应该放在下层 crate 里。
2. **一个 crate 应当能通过阅读它自身以及它下方的 crate 来理解。**正是这个性质让代码库可导航，也让并行开发成为可能。

`noxel-core` 除 `std` 之外不依赖任何东西。`noxel-render` 与 `noxel-world` 相互独立：渲染器不知道区块是什么，世界也不知道网格是什么。是 app 把它们连接起来。

## 逐个 crate 来看

### `noxel-core` —— 基础层

这里没有任何东西与游戏有关。这里的一切都是某种数据结构或函数，放进任何模拟系统里也同样合适。

| 模块 | 内容 |
|---|---|
| `math::vec` | `Vec2`、`Vec3`、`Vec4`；`Vec3::from_yaw` |
| `math::scalar` | `EPSILON`、`wrap_angle`、`angle_delta`、`rotate_towards`、`damp`、`damp_factor`、`tonemap_aces`、`linear_to_srgb`、`srgb_to_linear`、`div_floor`、`rem_euclid_i32` |
| `math::mat` | `Mat3`、`Mat4`（列主序，`get(row, col)`）、`look_at_rh`、`perspective_rh`（深度 `0..1`）、`orthographic_rh`、`inverse` |
| `math::quat` | `Quat`：yaw 提取、YXZ 欧拉角、slerp、`rotate_towards`、`look_rotation` |
| `math::shapes` | `Aabb`（slab 射线测试，`safe_inv`）、`Sphere`、`Ray`（Möller–Trumbore）、`Plane`、`Frustum`（正顶点测试）、`Rect`、`Transform` |
| `math::color` | `Color`（线性 `f32`）、`Color8`（sRGB 字节）、`Palette`、`blend_over` |
| `math::noise` | `value_2d`, `perlin_2d`, `simplex_2d`, `worley_2d`, `fbm_2d`, `ridged_2d`, `warped_fbm_2d`, `value_3d`, `tileable_value_2d`, `hash01_2d/3d`, `distance_to_segment_2d` |
| `math::mod` | `GridPos`、`ChunkPos`（**注意：`y` 就是 Z**）、坐标转换 |
| `rng` | `Pcg32`、`RngStream`（`for_chunk`、`for_grid3`、`fork`、`value_at`）、`ShuffleBag`、FNV-1a 哈希 |
| `time` | `GameClock`（固定步长、子步上限、`alpha` 插值）、`FrameTiming`、`Stopwatch`、`Profiler` |
| `jobs` | `JobPool`（作用域线程）、`parallel_for`、`parallel_chunks`、`join`、`Progress` |
| `pool` | `Handle<T>`（带世代）、`SlotMap`（`get_two_mut`）、`FreeList`、`BitSet` |
| `spatial` | `UniformGrid<T>`、`SpatialHash<T>`、`Bvh<T>`（射线/AABB/视锥查询，`any_hit_segment`） |

这些噪声函数是**基于哈希而非基于查表**的：任何坐标都无需其邻居即可采样。正是这一个选择让并行的世界生成成为可能（`adr/0006-deterministic-generation.md`）。

### `noxel-ecs` —— 实体

一个扁平的 `Vec<Box<dyn ErasedStorage>>` 里的稀疏集存储，正是它让多组件迭代方法可以进行安全的分裂借用。

| 模块 | 内容 |
|---|---|
| `entity` | `Entity`（索引 + 世代）、`EntityMeta`、与 slot map 句柄之间的相互转换 |
| `storage` | `Storage<T>` 稀疏集：插入、移除、`retain_alive`、变更计数器 |
| `world` | `World`：spawn、despawn、组件、资源、`for_each*` 系列、变更检测 |
| `scheduler` | `Scheduler<C>`：具名阶段、系统、逐系统统计 |

`World::for_each2_mut2` 及同类方法之所以存在，是因为借用检查器看不出两种组件类型位于不同的 `Box` 里。`World` 用 `pair_mut_by_index` 一次性证明这一点，此后迭代 API 就是安全的。

## 一帧的细节

```text
App::step(frame_dt)
│
├── debug.begin_frame(frame_dt)
│
├── fixed_update(frame_dt)
│   │  clock.begin_frame(frame_dt)
│   │  while clock.step() {                       // 0..max_substeps times
│   │      plugins.update(app, FIXED_DT)          // gameplay
│   │      physics.step(FIXED_DT)
│   │  }
│   └  returns the number of substeps
│
├── frame_update(frame_dt)
│   ├── plugins.frame(app, frame_dt)
│   ├── plugins.pre_cull(app, frame_dt)           // move the camera here
│   ├── camera.follow_with_velocity(focus, vel, frame_dt)
│   ├── view = camera.view(aspect)
│   ├── streamer.update(focus)                    // load/unload chunks
│   └── visible = visibility.update(input, settings)
│
├── render()
│   └── raster | hybrid | raytrace -> framebuffer
│
├── draw_overlays()
│   ├── plugins.draw(app, &mut framebuffer)
│   └── debug.draw(&mut framebuffer, Some(&view))
│
├── dump_frame(framebuffer)                       // if a dumper is attached
└── debug.end_frame(frame_ms)
```

### 为什么是这个顺序

**玩法在相机之前。**相机读取玩家的位置，所以玩家必须先移动。

**相机在流式加载之前。**流式加载器围绕相机加载区块。如果先跑它，它就会围绕上一帧的相机加载，于是世界晚一帧到达，玩家会在高速移动时看到区块在身后冒出来。

**流式加载在可见性之前。**可见性要同时针对相机视锥*和*遮挡索引做剔除。对一个尚未加载的区块做剔除毫无意义，而针对一个即将改变的场景做剔除则是白费功夫。

**可见性在渲染之前。**渲染器把 `VisibleSet` 作为参数接收；它从不自行决定要画什么。正因如此，可见性系统可以单独测试，也正因如此，可以在不碰它的情况下加入 GPU 渲染器。

**叠加层最后。**它们在图像着色完成之后画进帧缓冲，因此不会被遮挡，也不受光照影响。随后的 resolve 再一次性把整幅画面转换成 sRGB。

**固定更新在帧之内，而不是反过来。**一帧花了一秒，绝不能变成六十次物理步进。`GameClock` 会限制子步数量，并报告它丢弃了多少时间。

## 多线程

Noxel 通过 `JobPool` 使用 `std::thread`，仅此而已。没有 async 运行时，也没有线程局部状态。

目前有两处是并行的：

- **区块生成。**按构造就是确定性的（`adr/0006`），因此区块可以以任意顺序并行生成，无需任何协调。
- **光栅化。**帧缓冲被切分成互不相交的行带；每个行带把各自的 tile 光栅化进各自的切片。像素路径上没有锁、没有原子操作，也没有浮点重结合，因此并行与串行的结果逐位相同——这一点有测试断言。

`JobPool::parallel_for` 接收 `&mut [T]`，给每个工作线程一个互不相交的 `&mut`，因此数据竞争的缺席由借用检查器来证明，而不必靠评审者。

## 扩展点

| 你想 | 实现 |
|---|---|
| 新的渲染器（GPU、无头、ASCII） | `renderer::Renderer` |
| 玩法逻辑 | `app::Plugin` |
| 新的组件 | 任何 `'static` 类型，通过 `World` 挂载 |
| 新的物理形状 | `shape::ColliderShape`（再加一个窄相分支） |
| 新的生物群系 | `biome::BiomeTable` 中的一条记录 |
| 新的方块/tile 类型 | `TileSet` 资源中的一个 `TileDef` |
| 新的相机行为 | `camera::zone::CameraZone`，或插件的 `pre_cull` |
| 新的剔除规则 | `visibility::VisibilitySystem::update` 中的一个阶段 |

## 常见错误

**「我给 `noxel-render` 加了一条指向 `noxel-world` 的依赖。」**
这会经由 `noxel-app` 构成环，根本无法编译。方向规则不是风格问题：正是它让世界生成器独立于渲染器，也正因如此才可能有纯统计的无头运行。

**「我把玩法逻辑放进了 `Plugin::draw`。」**
`draw` 每个渲染帧运行一次；`update` 每个*固定*步运行一次，而一帧可能包含零个或多个固定步。放在 `draw` 里的玩法逻辑运行频率不对，还会破坏确定性。

**「我在 `Plugin::pre_cull` 里读了 `Scene`，又在 `Plugin::draw` 里改了它。」**
在这两者之间，可见性处理已经跑过了。在剔除之后修改场景，意味着 `VisibleSet` 描述的是一个已经不存在的场景。要么在 `pre_cull` 里改，要么接受一帧的延迟。

**「我把 `World` 做成资源了。」**
`World` 拥有各个存储；`Resource` 则住在它内部。这是两个不同的概念，把它们混在一起会得到一个读起来像类型错误的借用错误。
