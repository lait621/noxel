# 性能

Noxel 的目标是 320x180 到 960x540、每帧几千个三角形、跑在 CPU 上、不使用 GPU 也不引入依赖。在这个尺度上，帧预算花在少数几个地方，而几乎所有调优都是在选择*做多少工作*，而不是做得多快。

本指南涵盖时间花在哪里、如何测量、哪些杠杆真正撬得动它，以及如何写一个不会在慢机器上失败的性能测试。

## 帧时间花在哪里

`noxel-debug` 为帧的每个环节预置一份预算。下面这些是真实的名字 —— `Stats::new` 创建的就是这张列表，报告和叠加层打印的也是它们：

| 预算 | 额度 | 覆盖范围 |
|---|---|---|
| `update` | 4.0 ms | 固定更新阶段：插件的 `update` 钩子（玩法） |
| `physics` | 4.0 ms | `PhysicsWorld::step` |
| `visibility` | 1.5 ms | 视锥、距离、尺寸、遮挡与淡出 |
| `stream` | 3.0 ms | `WorldStreamer::update` —— 区块生成与淘汰 |
| `npc` | 4.0 ms | 人群步进（`docs/07-npcs.md`） |
| `render` | 6.0 ms | 整个渲染通道：几何、着色、后处理 |

关于这张表有两点。第一，这些额度是**重叠**的：`update` 是整个固定更新阶段，所以 `physics` 在它里面；而 `render` 是整个渲染调用，不是其中的某一个阶段。它们是各环节自己的告警阈值，不是一块饼切出来的份数；它们加起来刻意超过 60 fps 的一帧，这样就能在不牵动其他环节的情况下单独诊断某一个环节。

第二，目前引擎只记录了其中一部分。`DebugSystem` 会填 `render`（`record_render` 调用 `stats.spend("render", stats.ms_total, 0.0)`），其余由游戏调用 `record_section(name, ms)` 来填。`FrameSample` 的其他字段 —— `visibility_ms`、`stream_ms`、`npc_ms`、`physics_ms` —— 是存在的，但除非游戏去设置，否则哪里都不会打印；`App` 改为把区块数量记成计数器。如果你想要分环节的数字，就在调用点自己记录：

```rust
let started = noxel_core::time::Stopwatch::start();
// ... do the work ...
let ms = started.elapsed_ms() as f32;
app.debug_mut().record_section("physics", ms);
```

`FrameSample::unattributed_ms()` 是 `frame_ms - update_ms - render_ms`，在零处钳制；当帧很慢而没有任何预算超标时，这就是该看的数字。

## 如何测量

| 工具 | 它能给你什么 |
|---|---|
| `cargo run -p town-demo -- --stats` | 一个稳定下来的帧，加上完整的 `DebugSystem::report()` 文本 |
| `cargo run -p town-demo -- --world-info` | 种子生成的内容，不做渲染 —— 隔离生成成本最便宜的方式 |
| 帧时间曲线图 | `DebugConfig::frame_graph`，由 `DebugSystem::draw` 从 `Stats::frame_times` 绘制 |
| `HeadlessReport` | 均值、p95、最差、fps、片元数、射线数、实例峰值、常驻区块、区块字节数、导出的帧数 |
| `FrameDumper` | 每帧 PNG、PNG+深度，或原始 RGBA，外加 `dump::compare` 与 `diff_image` |
| `Stopwatch` / `Profiler` | 分环节与分层的 CPU 计时 |

`App::run_headless(frames)` 返回一个 `HeadlessReport`。该信的是 `p95_frame_ms`，不是 `mean_frame_ms`：一个构建可以平均 60 fps，却每秒卡顿两次，而卡顿正是玩家唯一注意得到的东西。`HeadlessReport::within_budget(ms)` 是断言形式，`summary()` 是一行日志形式。

```rust
let mut app = noxel_app::App::new(noxel_app::AppConfig::headless())?;
// ... add plugins ...
let report = app.run_headless(600);
assert!(
    report.within_budget(16.67),
    "p95 {:.2} ms — {}",
    report.p95_frame_ms,
    report.summary()
);
```

`FrameDumper` 写出 `frame_000123.png`，也可以写出深度表（`DumpFormat::PngAndDepth`）或原始小端 RGBA（`DumpFormat::Raw`），用于逐字节比较。`dump::compare(a, b)` 返回一个 `ImageDiff`，带有 `differing`/`total`、`max_channel_delta` 和 `squared_error`，而 `ImageDiff::within(max_ratio, max_channel_delta)` 就是黄金图像断言。因为渲染是确定性的（`docs/adr/0008-deterministic-rendering.md`），`within(0.0, 0)` 是一个正当的断言，而不是一个会偶发失败的断言。

### 分析某一个环节

```rust
use noxel_core::time::Profiler;

let mut profiler = Profiler::new();          // 16.67 ms budget, enabled
// Per frame:
profiler.begin_frame(0.0);
{
    let token = profiler.scope_begin("visibility");
    // ... work ...
    profiler.scope_end(token);
}
profiler.scope("physics", || {
    // ... work ...
});
profiler.end_frame();
if profiler.over_budget() {
    println!("{}", profiler.last_frame().to_table());
}
```

`Profiler` 是分层的：`ScopeSample` 携带 `depth`、`parent`、`calls` 和 `ms`，`FrameProfile::scope(name)` 查找其中一项，`walk` 会带着深度访问每一个作用域，`to_table()` 渲染出缩进的报告。`Profiler::disabled()` 什么都不记录，所以发行构建不付任何代价。

## 杠杆，按顺序

沿着这张表往下做。前三项比它们之后的所有项加起来都值钱。

| # | 杠杆 | 位置 | 大致收益 | 代价 |
|---|---|---|---|---|
| 1 | **内部分辨率** | `AppConfig::internal` | 平方关系：480x270 → 320x180 少了 2.25 倍的像素 | 精灵更粗糙；信箱边会随 `Viewport::integer_scale` 变化 |
| 2 | **可视距离** | `WorldConfig::view_distance_chunks` | 与加载的区块数成平方关系：6 → 4 是 81 个区块而不是 169 个 | 世界的尽头明显更近；要提高 `keep_distance_chunks` 做迟滞，否则区块会来回抖动 |
| 3 | **`min_screen_radius`** | `CullSettings` | 与阈值以下的实例数成正比 | 小物体会整个弹出视野；0.45 px 是像素边界，再往下剔除的就是本来就看不见的东西 |
| 4 | **遮挡剔除** | `OcclusionSettings::cull_occluded` | 在密集城镇里收益大，在开阔乡野约等于 0 | 「那个东西怎么不见了？」这类 bug；用 `cull_max_screen_radius` 把大物体排除在外 |
| 5 | **LOD / 更新比例** | `LodLevels`、`LodSelection` | 1–3 层的人群有 2–10 倍收益 | 远处的代理更新更少；只有阈值设得太激进时才看得出来 |
| 6 | **NPC 分层** | `docs/07-npcs.md` | 与离开近层的代理数量成正比 | 远处的转向质量 |
| 7 | **区块网格粒度** | 你的地形插件 | 更少更大的实例：每区块一个网格胜过每地块一个 | 剔除粒度更粗，区块到达时的重建尖峰更大 |
| 8 | **着色模式** | `ShadingMode` | `Raster` → `Hybrid` 是变贵的方向；`Hybrid` → `Raster` 是变便宜的方向 | 光线追踪的阴影和 AO |
| 9 | **阴影贴图尺寸** | `RenderSettings::shadow_map_size` | 与纹素成平方关系：2048 → 1024 少了 4 倍 | 阴影更软/更块状；还要检查 `Light::Directional::shadow_extent`，因为在很小的贴图上用很大的范围，是同一种损失却毫无节省 |

有两个看起来像性能旋钮、其实不是的东西：

- **`RenderSettings::backface_culling`** 本来就开着、本来就很便宜；关掉它省不下任何一半，还会破坏闭合网格的深度行为。
- 光线追踪器里的 **`temporal_blend`** 是用帧数换采样数，而不是用质量换速度。它是为静帧准备的正确杠杆，不是为玩法准备的。

## 写一个不会偶发失败的性能测试

断言一段*时长*的测试测量的是机器，而不是代码。它在你的笔记本上通过，在 CI 上失败，而且失败时什么也告诉不了你。改为断言一条**不变式** —— 无论什么机器都必须成立的性质：

| 与其 | 不如断言 |
|---|---|
| 「1000 个代理在 6.4 ms 内更新」 | `stats.active == 1_000 && stats.last_step_ms < 8.0` |
| 「每帧 4 ms」 | p95 上 `report.within_budget(16.67)`，并且 `report.fragments` 落在已知范围内 |
| 「流式加载很快」 | 第一次 update 时 `stats.generated_this_update == 13 * 13`，第二次为 `0` |
| 「内存不增长」 | 走 40 步之后 `streamer.memory_bytes()` 低于某个上界 |
| 「世界是稳定的」 | 两种生成顺序产生相同的字节 |

测试套件里已经有可以照抄的模式：

- `second_update_at_the_same_place_is_free` 断言的是*精确*的工作量（`generated_this_update == 0`，缓存大小不变），而不是一段时长。
- `memory_stays_bounded_over_a_long_walk` 在 40 次 update 上断言一个上界。
- `heights_are_continuous_over_a_small_step` 比较的是*推导出来的*数字：采样步长减半，最大变化量也必须大致减半。这样无需知道机器的速度就能抓到不连续。
- `resting_box_does_not_sink_over_six_hundred_steps` 跑 600 步并断言一个位置不变式（与解析高度的差在一毫米之内）。
- `determinism_is_bit_exact` 把同一个场景跑两遍并比较状态，`parallel_and_sequential_rendering_agree` 比较两条渲染路径。

当时长确实是测试对象时，就在同一次运行、同一台机器上测量两种配置之间的**比值**（粗 vs 细、1000 vs 100 个代理），并断言它们的相对次序，而不是绝对值。这样能扛住慢的 CI 机器；绝对阈值不能。

### 诚实地测量一次改动

1. **用 release profile。** 工作区的 `dev` profile 是 `opt-level = 1` 且 `overflow-checks = true`；`release` 是 `opt-level = 3`、fat LTO、一个代码单元、不开溢出检查。debug 的数字不是真实数字的小号版本，它是另一个数字。
2. **跳过预热。** 最初的几帧在生成区块、构建 BVH。demo 在开始上报之前会跑 12 个预热帧，正是这个原因；你也照做。
3. **保持其他一切不变。** 同一个种子、同一个内部分辨率、同一个 `fixed_dt`、同样的帧数、同一台机器、同样的电源状态。
4. **比较 p95，而不是均值。** 一个用罕见尖峰换来更好均值的改动，手感可能反而更差。
5. **一次只改一个杠杆**，并把设置和数字一起记下来。一个没有种子和分辨率的性能数字算不上测量。

## 常见错误

- **拿 debug 构建做基准测试。** `cargo run` 用的是 `dev` profile：`opt-level 1` 加溢出检查。请用 `cargo run --release`，并预期有数倍的差距。
- **上报第一帧。** 它要付区块生成、BVH 构建和阴影贴图分配的账。先预热，再测量。
- **只信 `mean_frame_ms`。** 均值会掩盖卡顿。`p95_frame_ms` 和 `worst_frame_ms` 就在同一份报告里 —— 去读它们。
- **把 `HeadlessReport::fps` 当成帧率。** `run_headless` 能跑多快就跑多快，从不休眠；它的 `fps` 是吞吐量，不是玩家会看到的节奏。要看节奏，请跑 `RunMode::Realtime { seconds, fps }`，它同样不休眠 —— 真正的时钟由*宿主*掌握。
- **开着调试叠加层做测量。** 叠加层要花片元、每帧构建一次面板，而且开了 `wireframes` 时每个绘制的盒子还要一次查询。测量时请用 `DebugConfig::minimal()` 或 `disabled()`。
- **忘了 `record_section` 只在 `record_sections` 打开时才有效。** `DebugConfig::disabled()` 会把它设为 false，你的测量就会悄无声息地消失。
- **把慢帧怪到渲染器头上。** 先看计数器：`culled/distance` 很大而 `drawn` 很小，说明可见性系统在正常工作；`considered` 巨大则说明场景里的实例比该有的多，那是制作问题，不是渲染问题。
- **调大 `max_cached_chunks` 来「抹平」流式加载。** 它只会抬高内存，并不会改变生成成本；而这个硬上限的存在，正是为了让一次长途行走无法无界地分配内存。改为一起调 `view_distance_chunks` 和 `keep_distance_chunks`。
- **在像素画目标上把 `min_screen_radius` 调到约 0.45 px 以下。** 在 320x180 下，一个亚像素物体要花掉一整个实例的设置成本，却毫无贡献；你是在花钱让剔除器不工作。
